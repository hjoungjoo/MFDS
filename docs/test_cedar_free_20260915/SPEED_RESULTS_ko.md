# 솔빙 검색 속도 개선

## 적용 내용

MF 후보 좌표를 소비하는 PiFinder의 Tetra3 검색을 최적화했다. native 검출기와
전처리 알고리즘은 유지한다. Cedar에도 공통으로 적용 가능한 검색 엔진 개선이며
MF 검출기 자체가 빨라졌다는 뜻은 아니다.

- 한 영상 패턴의 주변 해시를 NumPy로 일괄 계산한다. 기존 거리순/동률순을 유지한다.
- 해시 충돌 조회에서 슬롯별 NumPy 스칼라 연산과 임시 boolean 배열을 제거한다.
  uint64 오버플로와 전체 충돌 사슬 순서는 유지한다.
- 후보 수/순서, 검색 범위, 각 중심/전체 솔빙 시도의 기존1000ms 제한과
  품질 기준은 바꾸지 않는다.
- 이전 방식은 `TETRA3_SEARCH_OPTIMIZED=0`, 기본 최적화는 `1`로 선택한다.
  객체 생성 때 읽으므로 방식별 프로세스 또는 별도 Tetra3 객체로 비교한다.

개발 구름5장 프로파일에서 `_pattern_hash_to_index`가 82,837회 호출되며
2.71초, 패턴 조회가 2.72초를 차지했다. 프로파일링 시간은 오버헤드가 있으므로
아래 재생 측정에는 프로파일러를 쓰지 않는다.

## 측정 방법

`compare_search_speed.py`는 RAW/전처리마다 한 번 검출한 **같은 좌표**를 두
검색 방식에 공급하고 실행 순서를 교대한다. 각 방식은 별도 Tetra3 캐시를 쓴다.
검출+솔빙 시간은 공유한 검출 시간과 각 검색 시간을 더한 값이다. 캐시 생성,
카메라 IPC, SQM, UI, 마운트 동작을 포함하지 않는다. RAW 원본 SHA256으로
캐시 연결을 검증하고 상세 좌표는 로컬에 보관한다.

구름 앞16장은 개발용으로 제외하고 후속104장 중 누적 초기화를 제외한102장을
검증한다. 광해는 고정 장비
검증120장 중 전처리 초기1장을 제외한119장을 쓴다. 같은 프레임의 기존/개선
결과를 비교하며, 앞선 Cedar 비교 표와 실행 순서/캐시 조건이 달라 수치를
직접 이어 붙이지 않는다.

RMSE는 카탈로그 매칭의 각도 잔차(arcsec)이며 독립 기준 대비 절대 지향 오차가
아니다. PiFinder 문서에 남아 있던 pixels 표기도 코드에 맞춰 arcseconds로 수정했다.

## 같은 입력의 A/B 결과

시간은 ms. 중앙값/p95는 검출+솔빙이며 전처리 생성 시간은 제외한다.

| 입력 | 성공 기존→개선 | 중앙값 기존→개선 | p95 기존→개선 | RMSE 중앙값 기존→개선(초각) |
|---|---:|---:|---:|---:|
| 광해 RAW119장 | 118→119 | 80.6→61.6 | 1091.5→561.9 | 41.50→41.48 |
| 광해 전처리119장 | 119→119 | 39.0→34.4 | 85.9→60.5 | 27.67→27.67 |
| 구름 RAW102장 | 0→0 | 1195.8→943.5 | 1692.0→1389.7 | — |
| 구름 전처리102장 | 102→102 | 25.8→25.3 | 39.0→38.4 | 58.98→58.98 |

광해 RAW 중앙값은23.6%, p95는48.5% 감소했다. 구름 RAW 실패 처리 중앙값은
21.1%, p95는17.9% 감소했다. 전처리 구름의 기존 솔빙은 이미 짧아 전체 지연
개선은 작다. 구름 RAW의 검출 실패 원인 자체를 해결한 결과는 아니다.

RAW/전처리 총884개 방식별 결과에서 SEP 보조 호출은0회다. 전처리221장 모두
기존/개선의 좌표·RMSE·매칭 수·경로가 완전히 같다. 광해 RAW의 공통 성공118장
중115장도 같다. 3장은 중심 영역 검색이 제한 안에 완료돼 전체 영역 대신
중심 결과를 채택했다. 그중2장은 RMSE가 낮아졌고1장은62.52→63.31초각이다.
추가1장도 제한 안에 성공했다. 시간 제한이 있는 검색이므로 전체 결과가 언제나
비트 단위로 동일하다는 의미는 아니다.

개발15장(독립 검증에 미포함)의 RAW 중앙값은1149.6→620.8ms였다. 이 개발
수치를 후속102장의 개선율로 대신 사용하지 않는다.

## 실제 전처리 실행을 포함한 재생

각24프레임을 별도 프로세스에서 재생했다. 카메라 IPC/SQM/UI/마운트는 제외되며
여기는 전처리를 실제 실행한다. 고정 광해는 정상 비동기22회, 초기 동기2회다.
구름은 RAW 실패 때문에24회 모두 동일 프레임의 동기 복구를 한다. 구름 복구
재생은 앞24장을 사용해 정책을 확인했으며 독립 정확도 검증102장과 구분한다.

| 경로 | 중앙값 기존→개선(ms) | p95 기존→개선(ms) | 좌표 채택 기존→개선 |
|---|---:|---:|---:|
| 광해 정상 비동기 foreground | 112.7→68.6 | 1080.2→1014.7 | 22/24→22/24 |
| 구름 동일 프레임 복구(전처리 포함) | 2133.1→1725.9 | 3049.0→2344.5 | 18/24→18/24 |

광해 RAW는24/24 성공, 양쪽 bias 갱신6회이며 SEP 호출0회다. 초기 동기2회
중앙값은971.3→1074.6ms로 늘었고, 전처리 알고리즘은 그대로이므로 모든 단계가
빨라졌다고 주장하지 않는다. 별도 실행의 병렬 경합/부하 변동을 포함한 단일
재생 결과다. 정상 foreground p95는 여전히 약1초, 구름 복구 p95는2.34초다.
GOTO 실동작 지연을 보장하는 결과가 아니다.

6프로필 비교(각 RAW/전처리23장):

| 프로필 | RAW 성공 | 전처리 성공 |
|---|---:|---:|
| MF4p 기본 | 23/23 | 23/23 |
| MF2 | 23/23 | 23/23 |
| MF4p SEP 끔 | 23/23 | 23/23 |
| SEP | 22/23 | 23/23 |
| MF4o 원본 좌표 재측정 | 14/23 | 23/23 |
| MF8p | 6/23 | 23/23 |

MF2 실제 비동기 foreground 중앙값177.1ms 대비 MF4p는68.6ms여서 기본은
MF4p+auto를 유지한다. 별도 anchor 실험도 실행했다: RAW24/24 성공, RAW12회/
전처리+RAW변화량12회, 독립 background solver 확인, foreground 중앙값76.6ms.
1.2/2.5초 지연 좌표 재생 비교도 완료했다. anchor를 서비스 기본으로 바꾸지 않는다.

## 검증 및 적용 범위

- Python 전체 단위 테스트: 2326통과, 2skip, 723deselected, 기존 경고8개.
  새 검색 테스트15개는 scalar/batch 해시의 uint64 오버플로, 충돌 순서,
  빈 슬롯, 자료형과 이전 방식 선택을 검사한다.
- native 빌드 및6/6 테스트, canonical23개 파일/라이선스 범위 검사 통과.
- 스모크7개, PiFinder/canonical Python Ruff 검사, MyPy204개 파일 검사 통과.
- 총884개 A/B 결과의 같은 입력 연결, 후보 상한48개, 성공 품질 기준을 검사했다.
- 정렬/보정/RAW 실패 대기, MF 우선/SEP 보조, 좌표 저장 정책은 유지했다.
- 운영 PiFinder PID715, Cedar PID708, drop-in 없음과 운영 checkout 무변경을 확인했다.
  운영 서비스/부팅 경로를 바꾸지 않고 승인된 두 테스트 브랜치에 적용한다.
