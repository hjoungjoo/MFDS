# 전처리 실행 위치와 중복 계산 실측

2026-09-15. [작업 전 계획](PREPROCESS_PLACEMENT_PLAN_ko.md).
기준 전처리는 MF `7bcefb9`, 비교 도구·개선 코드는 `4347966`이다.

## 비교 구조와 해석

| 모드 | 전처리 위치 | MF 검출 | 마스크 캐시 |
|---|---|---|---|
| `current` | 호출 프로세스 | 별도 native 프로세스 | 없음 |
| `moved` | 공유 메모리 시험 프로세스 | 별도 native 프로세스 | 없음 |
| `colocated` | 공유 메모리 시험 프로세스 | 같은 시험 프로세스의 ctypes | 없음 |
| `colocated_cached` | 공유 메모리 시험 프로세스 | 같은 시험 프로세스의 ctypes | 사용 |
| `current_cached` | 호출 프로세스 | 별도 native 프로세스 | 사용 |

모든 모드는 NumPy/SciPy 전처리와 배경 스케일 작업자 3개를 사용한다.
실행 위치를 바꾸기 전부터 배경 스케일 계산은 병렬이다.
`colocated*`는 기존 ctypes 비교 경로를 이용한 **내부 성능 모형**이다.
전처리를 C++로 이식한 실행 파일이나 FSL로 재라이선스한 산출물이 아니다.
따라서 그 모드의 수치로 향후 native 전처리의 성능/배포 적합성을 확정할 수 없다.

`current_cached`는 기존 실행 구조를 유지하면서 과거 프레임의 별 후보
형태 분류를 반복하지 않는다. 각 프레임의 float16 양자화 이후 마스크를
한 번 계산하고 시간 창에서 함께 제거한다. 합산 순서·출력·진단 계산은 유지한다.
1080×1920, 5장 시간 창에서 추가 메모리는 약 9.9MiB/누적기다.
동시에 두 누적기가 가득 차면 약 19.8MiB가 추가된다.

## 측정 조건

- 고정 광해 검증 자료 `20260915_fixed_validation`: 처음 20장, 순서 교대 2회.
- 구름 자료 `20260903_cloud_coordinate_jitter`: 19번째부터 20장, 순서 교대 2회.
- 각 반복 첫 4장은 5장 시간 창 준비 구간으로 집계에서 제외한다.
  데이터별 16개 서로 다른 영상 × 2회 = 모드별 32회다.
- RAW 1080×1920 uint16, MF4p, 원본 TIFF와 메타데이터 SHA256 일치 확인.
- geometry fingerprint를 사용하며 노출/게인 변화만으로 시간 창을 초기화하지 않는다.
- 같은 프로세스에서 모드를 교대하며 한 번에 한 전처리만 실행한다.
  별도의 린트·타입 검사·테스트를 시간 측정과 동시에 실행하지 않는다.
- 모드별 독립 Tetra3 인스턴스, 전처리 후 같은 솔빙 경로 사용.
- 전처리 영상·evidence 해시·별 좌표·밝기·진단 정보를 모든 프레임에서 정확 비교.
- `pipeline_ms`에는 공유 메모리 입출력, 결과 수신과 검증용 evidence 해시 계산이
  포함된다. `total_ms`는 여기에 솔빙을 더한 값이다. 검증 도구의 비용까지 포함한
  비교치이며 실제 노출→좌표 발행 지연은 아니다.
- 프로세스 시작은 별도로 기록한다. Python 시험 프로세스 시작 시간에는
  비교 도구의 Python 의존성 import가 포함되어 native worker 시작과 다르다.

추가 병렬 시험은 `current`, `current_cached`, `colocated_cached`를 비교한다.
같은 자료 각 12장, 1회, 첫 4장 제외. 전처리 작업을 진행하며 주 스레드에서
최대 10Hz로 같은 RAW를 반복 검출한다. RAW 한 번이 100ms를 넘으면 다음 호출은
이전 호출이 끝나야 시작한다. 카메라 입력·RAW 솔빙·좌표 발행·GOTO를 포함하지
않으므로 결과는 검출 경합 시험으로 해석해야 한다.
구름의 첫 병렬 시험에서 RAW p95 증가가 보여 같은 조건을 2회 더 반복했다.
이는 새로운 우려를 확인하기 위한 추가 측정이며 첫 결과도 함께 보관한다.
운영 서비스를 유지한 장비의 제한된 기록 재생이므로 모든 광해·진동·부하에서
동일한 개선 비율이나 GOTO 지연 상한을 보장하는 결과가 아니다.

## 실측 결과

### 전처리 + 검출 + 솔빙 결과

단위 ms, p50 / p95. 데이터별 모드당 32회(16개 영상 × 2회).

| 구조 | 고정 광해 검증 | 구름 |
|---|---:|---:|
| 기존 `current` | 1207.0 / 1382.9 | 1169.9 / 1348.5 |
| 위치만 분리 `moved` | 1193.3 / 1394.9 | 1143.6 / 1339.1 |
| 전처리+검출 통합 모형 `colocated` | 1152.5 / 1405.7 | 1156.0 / 1381.3 |
| 통합 모형+캐시 `colocated_cached` | 1039.9 / 1278.8 | 1001.5 / 1200.4 |
| **기존 구조+캐시 `current_cached`** | **1076.6 / 1211.8** | **1051.1 / 1215.6** |

기존 구조에 캐시만 적용하면 중앙값은 검증 **10.8%**, 구름 **10.2%**,
p95는 각각 **12.4%**, **9.9%** 감소한다. 전처리만의 중앙값은 검증
1154.4→1014.3ms, 구름 1126.1→1017.4ms다.

실행 위치만 분리하면 전체 중앙값은 1.1%/2.2% 감소하지만 검증 p95는
오히려 늘었다. 캐시 없는 통합 모형도 양쪽 데이터 p95가 늘었다.
합친 최적화 모형이 가장 낮은 중앙값을 보였으나 검증 p95에서는 기존
구조+캐시가 더 낮다. 작은 실행 시간 차이를 모두 IPC 제거의 효과로
해석하면 안 된다. 동일 전처리 계산도 실행 위치·메모리·호스트 부하에 따라
변동하며, 이번 시험은 C++ 전처리 구현의 속도를 측정한 것이 아니다.

5개 방식 모두 데이터별 32/32 솔빙 성공, SEP 사용 0회다.
시간 창 준비 구간을 포함한 **400개 처리 결과**의 전처리 영상·evidence·검출
좌표·밝기·진단이 기준과 정확히 일치했다. 집계 구간의 솔빙 결과(좌표,
RMSE, 매칭 수, 경로)도 모두 기준과 같다. RMSE p50/p95는 검증
26.00/30.18 arcsec, 구름 81.66/94.42 arcsec이다. 이는 카탈로그 매칭 잔차이며
마운드 실제 지향 오차의 측정값은 아니다. 정확도를 개선한 변경이 아니라
같은 결과를 더 적은 반복 계산으로 얻는 변경이다.

## RAW 병렬 부하 결과

검증은 모드별 8회, 구름은 첫 시험과 추가 2회를 합쳐 모드별 24회다.
RAW는 전처리가 진행되는 동안 반복 호출한 검출 시간이며 솔빙을 포함하지 않는다.
전처리 완료 시 검출 반복을 멈추므로 모드별 RAW 호출 수가 다르다.
이는 전처리가 동작 중인 조건의 지연 통계이며 동일 고정 시간 동안의
전체 RAW 프레임 지연 통계와 구분해야 한다.

단위 ms, p50 / p95.

| 자료 | 구조 | 전처리+검출+솔빙 | 병렬 RAW 검출 | RAW 호출 수 |
|---|---|---:|---:|---:|
| 검증 | 기존 | 1245.1 / 1444.2 | 37.2 / 74.1 | 104 |
| 검증 | 기존+캐시 | **1122.8 / 1357.8** | 38.3 / 70.4 | 96 |
| 검증 | 통합 모형+캐시 | 1205.3 / 1308.5 | 41.8 / 73.3 | 97 |
| 구름 3회 합산 | 기존 | 1444.3 / 1786.7 | 116.2 / 187.6 | 286 |
| 구름 3회 합산 | 기존+캐시 | **1363.3 / 1641.8** | 120.0 / 193.5 | 259 |
| 구름 3회 합산 | 통합 모형+캐시 | 1361.1 / 1616.9 | 120.6 / 183.1 | 257 |

첫 구름 시험에서 기존+캐시 RAW p95는 172.3→209.9ms로 늘었다.
추가 2회만 집계하면 반대로 191.4→183.1ms로 줄었으며, 전체 3회 합산은
187.6→193.5ms다. 첫 결과를 버리거나 유리한 회차만 선택하지 않는다.
**RAW 응답성 개선은 입증되지 않았다.** 병렬 부하에서는 완료 시간 이득도
고정 비율이 아니며 반복별 편차가 있다.

구름 합산에서 통합 모형은 기존+캐시와 전체 중앙값 차이가 약 2ms이고
RAW p95는 약 10ms 낮지만, 검증 자료에서는 전체 중앙값이 약 82ms 높다.
따라서 전처리 위치 통합을 모든 조건에서 더 빠른 기본 구조로 정할 근거는
부족하다. 공유 메모리 경계/우선순위/실제 native 전처리를 함께 구현한다면
그 최종 구현으로 다시 측정해야 한다.

### 반영과 검증

- **테스트 기본은 기존 프로세스 구조+마스크 캐시**로 한다. 무부하에 가까운
  전처리+솔빙 이득은 약 10–11%, 구름 병렬 부하 합산에서는 약 5.6%다.
  동시에 RAW 지연이 항상 줄거나 GOTO가 빨라진다는 뜻은 아니다.
- 전처리/검출 통합은 비교 도구의 모드로만 유지한다. 기존 RAW 실패·정렬·보정
  대기 정책과 MF 우선/SEP 보조 정책은 그대로다.
- 총 544회 처리(기준 128회, 비교 416회)에서 영상/evidence/검출/진단의 차이가
  없었다. 집계 구간의 전처리 솔빙 416회 모두 성공했고 결과도 기준과 같았다.
- 단위 테스트 **2364 passed, 2 skipped**, 기존 경고 8개. 신규 회귀 테스트는
  오래된 프레임의 캐시 제거와 reset 후 영상 크기 변경을 검사한다.
- 관련 전처리/검출 테스트 60개, smoke 7개, Ruff, 변경 Python 파일 format,
  MyPy 205파일, 라이선스 범위 검사, diff 공백 검사 통과.
- 운영 `pifinder.service` PID715, `cedar_detect.service` PID708의 기존 실행 경로와
  빈 DropInPaths를 확인했다. 운영 소스·서비스·부팅 설정은 바꾸지 않았다.
- 상세 결과는 로컬 `PiFinder_test_data/results/placement_*.json`에 보관하고,
  좌표 없는 [집계 JSON](preprocess_placement.summary.json)만 저장소에 포함한다.
  초기 `placement_pilot.json`은 준비 시험이므로 최종 시간 표에서 제외했다.

## 재현

PiFinder 테스트 저장소의 Python 환경에서 실행한다. 원본과 자세한 좌표는
로컬 데이터 디렉터리에만 저장한다. 기존 출력 파일을 덮어쓰지 않는다.

```bash
git -C /home/pifinder/mf_detect_star_test show 7bcefb9:integrations/pifinder/PiFinder/mf_star_only_preprocess.py > /home/pifinder/PiFinder_test_data/work/preprocess_placement/reference.py
cd /home/pifinder/PiFinder_test/python
PIFINDER_DATA_DIR=/home/pifinder/PiFinder_test_data PYTHONPATH=.:scripts \
  /home/pifinder/PiFinder/python/.nox/unit_tests/bin/python \
  scripts/benchmark_preprocess_placement.py CORPUS CACHE NEW_RESULT.json \
  --reference /home/pifinder/PiFinder_test_data/work/preprocess_placement/reference.py \
  --implementation PiFinder/mf_star_only_preprocess.py \
  --frames 20 --repeats 2
```

구름은 `--start 18`을 추가한다. 병렬 시험은 `--frames 12 --repeats 1
--raw-probe --modes current,current_cached,colocated_cached`로 바꾸며 구름일 때
`--wide`도 지정한다. corpus/cache 경로는 각 데이터에 맞춘다.

운영 서비스·부팅·카메라·마운드는 변경하지 않는다. 라이선스 범위도 유지한다.
RAW 실패·초기 안정화·정렬·보정 때 같은 프레임 전처리를 기다리는 정책은 같다.
