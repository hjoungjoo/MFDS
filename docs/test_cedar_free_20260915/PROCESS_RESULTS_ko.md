# MF 독립 프로세스·공유 메모리 적용 결과

2026-09-15. [작업 전 계획](PROCESS_PLAN_ko.md)에 따라 테스트 기본을
`MF_DETECT_TRANSPORT=process`로 전환했다. MF4p 검출, SEP 보조 조건, RAW/전처리
스케줄과 정렬·보정 중 동기 대기 정책은 유지한다. 운영 서비스는 전환하지 않았다.

## 구현

- C++ `mf_detect_star_server`는 PiFinder/Python 없이 실행한다. 빌드 시 MF native
  코드만 연결하며 동적 의존성은 libstdc++/libm/libgcc/libc와 Linux loader다.
- Linux memfd에는 uint16 이미지 바이트만 저장한다. 이름 없는 공유 메모리이므로
  `/dev/shm` 파일이나 Python resource tracker 등록을 남기지 않는다.
- 호출 스레드별 지속 실행 worker/버퍼를 재사용한다. RAW와 전처리 검출은
  서로 다른 worker로 병렬 실행한다. 제어는 pipe, 결과는 float32 좌표/flux다.
- 요청 번호와 제출 시각을 응답에서 대조한다. 요청 제한 기본 500ms, 최초 시작
  대기는 최소 2초다. EOF/오류/timeout 시 worker를 종료·회수하고 기존 SEP
  정책을 따른다. 다음 호출에서 재시작하며 ctypes로 자동 우회하지 않는다.
- 정상 종료, 스레드 종료, fork 이후 격리, 부모 강제 종료를 처리한다.
  memfd는 크기 변경을 seal하고 서버는 이미지 범위를 검증한다.
- 직접 호출은 `MF_DETECT_TRANSPORT=ctypes`로 비교 가능하다. 서버 경로는
  `MF_DETECT_SERVER`, 직접 라이브러리 경로는 `MF_DETECT_LIBRARY`로 명시한다.
  별도 systemd 등록 없이 호출 프로세스가 worker를 관리한다.
- [독립 프로토콜과 예제](../PROCESS_PROTOCOL.md). 실제 LICENSE는 변경하지 않았다.
  프로세스 경계 구현은 GPL 결합 배포의 법률적 확정을 의미하지 않는다.

## 같은 영상의 직접 호출 / 프로세스 비교

고정 광해 검증 120장 중 warmup 1장을 제외한 119장, 구름 자료의
`--start 18 --frames 102` 중 전처리 재시작 2장을 제외한 100장을 사용했다.
각각 RAW/캐시 전처리 × 두 실행 방식을 교대로 측정했다. 총 876개 결과,
438개 검출 쌍이다. 캐시 생성 시간은 이 표에 포함하지 않는다.
초기 광해 탐색 실행은 타입 검사와 겹쳐 시간 평가에서 제외했고, 다른 검사
작업 없이 실행한 controlled 결과를 사용한다. 운영 서비스는 계속 동작했다.

| 자료 | 성공 직접→프로세스 | 검출 중앙값(ms) | 검출 p95(ms) | 검출+솔빙 중앙값(ms) | 검출+솔빙 p95(ms) |
|---|---:|---:|---:|---:|---:|
| 광해 RAW | 119/119→119/119 | 24.1→27.7 | 28.6→41.1 | 61.5→72.1 | 582.3→578.6 |
| 광해 전처리 | 119/119→119/119 | 24.2→28.2 | 31.7→38.5 | 33.5→38.2 | 54.6→68.7 |
| 구름 RAW | 0/100→0/100 | 79.8→84.1 | 106.2→116.4 | 995.6→993.6 | 1354.1→1440.2 |
| 구름 전처리 | 100/100→100/100 | 18.3→21.7 | 21.8→31.2 | 23.4→27.0 | 31.6→43.1 |

**438/438 검출 쌍의 좌표와 flux가 완전히 같다.** 전처리 219장 모두 솔빙
좌표·Roll·RMSE·매칭 수·검색 경로도 같고, 모든 비교에서 SEP 호출은 0회다.
솔빙 성공/실패가 바뀐 프레임은 없다. 검출 중앙값 추가 비용은 약 3.4~4.3ms다.
최초 검출은 광해 process 27.0ms / ctypes 24.6ms였으나 각 1회 값이며 startup p95가 아니다.

광해 RAW 119장 중 118장은 솔빙 결과도 동일했다. `raw_040`은 같은 검출 좌표로
직접 호출 쪽은 중심 검색(RMSE 34.40 arcsec, 15개 매칭), 프로세스 쪽은 시간
제한 후 전체 검색(RMSE 57.10 arcsec, 31개 매칭)을 택했다. 따라서 모든 솔빙
품질이 비트 단위로 동일하다고 표현하지 않는다. 같은 좌표 배열로 IPC 없이
8회 반복 솔빙해도 첫 회 전체 검색, 이후 7회 중심 검색이 재현됐다.
이는 기존 검색 제한/캐시 상태에 따른 경로 변동이며 좌표 전달 오류의 증거는 없다.
검색 제한을 늘려 GOTO 지연을 감추는 변경은 하지 않았다.

## 실제 전처리 계산을 포함한 auto 재생

각 조건 24프레임을 별도 Python 프로세스에서 실행했다. foreground 시간에는
필요한 RAW/전처리 솔빙·복구가 포함되지만 카메라 IPC, SQM, UI, 마운트는 제외된다.

| 조건 | 중앙값 직접→프로세스(ms) | p95 직접→프로세스(ms) | 좌표 채택 직접→프로세스 |
|---|---:|---:|---:|
| 광해 정상 비동기(22회) | 107.4→78.8 | 1012.0→1029.3 | 22/24→22/24(전체) |
| 광해 초기 동기(2회) | 1100.9→1081.4 | 1122.9→1148.8 | 22/24→22/24(전체) |
| 구름 동기 복구(24회) | 1703.8→1754.3 | 2553.5→2312.5 | 18/24→18/24(전체) |

광해 RAW는 두 방식 모두 24/24 성공, 초기 동기 2회/정상 비동기 22회다.
구름 RAW는 모두 실패해 24회 모두 같은 프레임의 동기 전처리 복구를 실행한다.
실제 재생도 SEP 호출은 0회다. 광해 bias 갱신은 6→7회로, 병렬 완료 시점의
차이가 있으므로 모든 스케줄 이벤트가 동일하다는 뜻은 아니다. 각 조건 1회씩의
재생이며 운영 부하·캐시·병렬 경합 변동이 있다. 비동기 중앙값 감소나 구름 p95
감소를 IPC가 항상 더 빠르다는 증거로 사용하지 않는다.

## 검증과 적용 범위

- 전체 단위 2361통과/2skip/723deselected(기존 경고 8개). 이후 종료 검증 2개
  추가 후 관련 검출 테스트 총 45개 통과. 추가 테스트는 mmap 범위/EOF와
  부모 강제 종료 후 worker 종료를 실제 프로세스로 검증한다.
- native 6/6, 스모크 7개, Ruff 및 변경 파일 format, MyPy 205개 파일 통과.
- 16개 native 모드/배율 조합의 직접 호출 동등성, 독립 병렬 버퍼, worker 재사용,
  해상도 변경, 강제 종료/재시작, timeout, 오래된 응답, fork 격리를 검사했다.
- canonical 파일/라이선스 검사와 변경 shell 문법 검사 통과. 라이선스 전문은 같다.
- 운영 PiFinder PID 715, Cedar PID 708과 실행 경로 유지, DropInPaths 비어 있음.
  운영 checkout/main, 부팅 unit, 카메라/마운트 설정을 바꾸지 않았다.
- 마운트 미연결 상태이므로 실제 GOTO 이동·정착 시간과 신선한 실시간 관측은
  검증하지 않았다. 기존 기록 기반 검증이며 이 결과로 GOTO 지연을 보증하지 않는다.

## 재현 및 기록

```bash
PYTHONPATH=python python3 python/scripts/compare_detector_transport.py CORPUS CACHE NEW_RESULT.json --frames 120
MF_DETECT_TRANSPORT=process PYTHONPATH=python python3 python/scripts/benchmark_auto_detector.py CORPUS CACHE NEW_AUTO.json --mode mf4p --frames 24
```

구름 비교에는 `--wide`, paired holdout에는 `--start 18 --frames 102`를 사용했다.
실제 서비스 전환을 별도로 요청할 때만
`scripts/test_runtime.sh start mf4p auto process` 또는 `... ctypes`를 사용한다.
이번에는 전환 명령을 실행하지 않았다.

측정 구현은 native `b316029`, PiFinder `d806f6a0`이다. 이후 변경은 종료 테스트와
문서/집계다. 집계는 [process_transport.summary.json](process_transport.summary.json),
상세 좌표·원본은 로컬 `PiFinder_test_data/results/process_*` 및 원래 corpus에
보관한다. 마지막 Git 참조 갱신은 이 검증된 소스를 테스트 브랜치에 연결한다.
