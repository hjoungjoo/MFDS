# 2단계 — 정확도 실험과 계산 최적화

## 작업 전 판단

같은 전처리 출력으로 비교했을 때 MF와 SEP가 공유하는 후보 좌표 차이는 매우 작았다(현재 장면 개발 30장, 가까운 후보 1,181쌍의 거리 중앙값 0.0043 px). 큰 RMSE 차이는 좌표 재측정보다 후보 선택/순서에 민감했다. 원본 aperture 재측정, Gaussian-window 재측정, 후보 16/24/32개 제한은 정확도 이득이 없어 기본값으로 채택하지 않는다. 검출 response 순서를 유지하는 실험에서는 개발 30장의 MF RMSE 중앙값이 49.21에서25.57 arcsec로 개선됐다.

구름 개발 16장 이후의 평가 102장은 SEP와 MF response 순서 모두102/102 솔브. RMSE 중앙값59.68/59.38 arcsec, p95 101.84/97.97 arcsec. 현재 최초180장 전체 비교에서도 MF response 순서는179/179 솔브였지만, 좌표 산포는 SEP보다 큰 구간이 있었다. RMSE와 pointing 반복정밀도를 구분해 보고한다.

## 속도 작업

Native gprof에서 mesh 보간이 샘플 CPU 시간 약23%를 차지했다. 축 보간 인덱스/가중치를 프레임마다 한 번 계산하고 배경과잡음이 공유하도록 변경했다. Gaussian convolution의 tap 계산은 행의 연속 메모리 순서로 바꿔 SIMD가 가능하도록 했다. 필터 계수, threshold, 경계 확장, 누적 순서를 유지하며 fast-math를 사용하지 않았다.

고정된 변경 전 ABI 라이브러리와 변경 후 라이브러리를 같은 원본/전처리 24장에서 교대로 3회 측정했다. 반환 후보 수·좌표·flux가 모두 동일했다(좌표/flux 최대차0). 검출 코어 중앙값118.89→96.14 ms, p95 149.22→122.57 ms. 동시 운영 및 실험 부하가 있어 절대 속도는 참고값이다.

Python 전처리는 evidence/capped/support 전체 시간창 세 벌 대신 프레임별 순차 누적으로 바꿨다. 기존 float16 양자화는 유지하고 보관 시 한 번 float32로 승격해 반복 변환을 줄였다. 보관 메모리는 약40 MiB 늘지만 최대 시간창 임시 배열 약120 MiB를 만들지 않는다. 전처리10장의 출력 픽셀, evidence, 진단값이 변경 전과 완전히 동일했다. 교대 측정 중앙값3358.52→3158.69 ms, p95 4206.15→3393.04 ms이며 동시 부하를 포함한다.

## 보존한 계약

운영 소스/서비스/부팅 설정을 바꾸지 않았다. 프레임ID·노출시각과 IMU anchor, 움직일 때 누적 reset, GOTO의12초 fresh-solve 대기/노출나이 한계를 그대로 유지했다. 테스트 설정에서 mount_control과 tracking guide는 비활성화했다. 실제 마운트가 없으므로 GOTO 정확도·정착시간·추적성능은 실측하지 않았다.

## 검증과 다음 단계

C++ 합성5/5, native ABI/합성좌표6개, 전처리/스케줄/바이어스32개, 검출/클라우드/프레임 계약43개 통과. 전체 첫 검사2,274개 및 mypy201파일 통과. 최종 전체검사는 변경된 시간 누적을 포함해 다시 수행 중이다.

개발에 사용하지 않은 현재120장 RAW를 추가 수집했다(120개 고유SHA256, 설정 전후 동일). 같은 전처리 출력으로 SEP와 native response 순서를 비교하고, 최종 좌표 산포와 전체지연을 다음 문서에 남긴다. SEP가 기본 backend이며 native 및 원본 재측정은 명시적 테스트 선택이다.
